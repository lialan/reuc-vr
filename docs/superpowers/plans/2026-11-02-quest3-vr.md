# Quest 3 VR port — plan

Goal: Resident Evil: The Umbrella Chronicles (RBUE08) playable on Quest 3 as a native OpenXR app: stereo 3D world, controller as the light gun, at the headset's frame rate. The GPU (Adreno 740) is the expected bottleneck, so every GPU decision is measured on the headset, never on the Mac.

Base: branch `quest3-vr`, on the macOS port (`45fa591`). The POSIX platform layer from that port (`*_posix.cpp`: memfd guest memory, pthreads, signals, savefs on openat) was written to compile for Android.

Reference implementation: gse-recomp's Quest stack (`~/Downloads/VR/gse-recomp/quest`, `lindberghrecomp/src/renderer/vulkan/openxr.cpp`, `stereo_projection.c`, `xr_actions.c`, `quest/run_vulkan_xr.py`). Patterns are copied and adapted, not linked.

Headset discipline: every device run goes through `quest3-lock` (exit 75 = busy, the GSE session shares the headset; retry), Guardian paused for scripted runs (`setprop debug.oculus.guardian_pause 1`, restored after).

## Design

- **Process model.** `libmain.so` loaded by an `SDLActivity` subclass (SDL3's Android Java, already in the fetched SDL3 source). SDL keeps audio (AAudio), gamepad and lifecycle; no SDL window or SDL Vulkan surface in VR.
- **Vulkan through OpenXR.** Instance and device come from `xrCreateVulkanInstanceKHR` / `xrCreateVulkanDeviceKHR` (XR_KHR_vulkan_enable2). The renderer gets a `PresentTarget` abstraction: SDL swapchain (desktop) or XR swapchain (Quest).
- **Stereo by multiview.** A frame is ~19 packets (scene, EFB copies, the game's own post chain reading those copies, HUD). Everything up to the end of the post chain renders with `viewMask = 0b11` into 2-layer targets; EFB copies of those passes become 2-layer array textures, sampled at layer `ViewIndex`. One recording, one submission, shared vertex work.
- **Per-eye camera.** The game's position matrices are already view space and its projection is a separate push constant (`smoke.slang` `Projection`). Perspective draws push `P_eye · T_eye`: `T_eye` = the eye's pose relative to the anchored head pose (yaw-recentred), translation scaled to game units; `P_eye` = asymmetric frustum from the XR fov tangents with the game's own near/far. The game's camera (on-rails motion) is untouched; the head moves on top of it.
- **HUD.** Orthographic draws after the post chain (HUD, reticle, menus) render once, mono, into a transparent target shown as an OpenXR quad layer in front of the player. Menus and movies (no perspective scene) use the same quad: the flat-screen mode is this layer alone.
- **Light gun.** Controller aim pose → ray in the head-anchored space → game view space → projected with the game's unmodified projection → `host_wii_pointer(x, y)`. Trigger = A (fire), grip/B = reload (Wii shake), stick/X/Y = the game's B/1/2/− mappings as the desktop gamepad does. Haptic pulse on fire.
- **Frame pacing.** xrWaitFrame/xrBeginFrame/xrLocateViews at the start of the game frame's first packet; xrEndFrame after the present packet. Display rate and game rate chosen by measurement (72/90/120 Hz; game at its native 30 or `--unlock-60fps`), compositor reprojection fills display frames the game does not render.

## Phase A — Android build, CPU side on the device

### Task A1: cross-compile for Android arm64
- `scripts/build-android.sh`: NDK 27.3 (`~/Library/Android/sdk/ndk/27.3.13750724`), `android.toolchain.cmake`, `ANDROID_ABI=arm64-v8a`, `ANDROID_PLATFORM=android-29`, `UC_TARGET_CPU=cortex-a78c` (XR2 Gen 2 big cores; also runs on its A55-class cores' ISA? check — fall back to `armv8.2-a+fp16+dotprod` if not), reusing the translator output in `generated/` (the translator runs on the host; the build only compiles its output).
- Fix what fails: `exe_path` (`/proc/self/exe`), `renameatx_np`→`renameat2`/`link`-based no-replace, QoS→`setpriority`/`sched_setaffinity`, `libunwind` symbols, `shm_open`→memfd, fonts (bundled), no `posix_spawn` probe.
- Gate: `uc_smoke`, `test_guest_mem`, `test_sched`, `test_ppc_float`, `test_savefs` built as Android executables, pushed to `/data/local/tmp`, all pass on the Quest.

### Task A2: headless boot on the device
- `uc --headless --seconds 30` as an Android executable against the game data pushed to `/data/local/tmp/reuc/game`.
- Gate: exit 0, retraces counted, no watchdog exit 4. Record guest CPU time per frame (the CPU budget for VR).

### Task A3: APK and runner
- `quest/` Gradle project (AGP as in gse-recomp, compileSdk 35, minSdk 29): `UcActivity extends SDLActivity`, manifest with `com.oculus.intent.category.VR`, `org.khronos.openxr.intent.category.IMMERSIVE_HMD`, head-tracking feature, supportedDevices, `profileable shell=true`; `libmain.so` + `libSDL3.so` + `libopenxr_loader.so` (Khronos 1.1.49, `~/Downloads/VR/deps/oxr`); shaders and pipeline seed as assets.
- Game data: streamed by the runner into the app's internal `files/game` with `run-as` (shell-staged external storage is unreadable to apps on current firmware).
- stderr/stdout → logcat (tag `uc`) and `files/runtime.log`.
- `scripts/quest/run.py`: build check, install, stage data once (hash-checked), `env.txt`, start, stream logcat, pull logs/captures, under `quest3-lock`.
- Gate: the APK starts on the Quest and boots headless-equivalent (game runs, no XR yet) — log shows retraces.

## Phase B — OpenXR session, flat virtual screen (first playable)

### Task B1: XR session and Vulkan through OpenXR
- `renderer/xr/openxr_session.{h,cpp}` adapted from gse-recomp `openxr.cpp`: loader init with JavaVM/Activity, instance (vulkan_enable2, android_create_instance; optional FB foveation, display refresh rate, performance settings, android thread settings), session, LOCAL space recentred on focus, event loop, refresh-rate request.
- Renderer: `PresentTarget` split out of `vulkan_renderer.cpp`; XR target = a quad-layer swapchain (RGBA8 sRGB, game's output aspect). Instance/device creation callbacks for the XR path (extension lists merged with the renderer's needs).
- Gate: on the Quest, title screen visible on a ~3 m wide screen 3 m ahead; logs show xrEndFrame every game frame.

### Task B2: controllers as the light gun
- `game/xr_input.cpp`: touch-controller action set (aim pose, trigger, squeeze, A/B/X/Y, sticks, menu, haptics) adapted from `xr_actions.c`; ray ∩ screen quad → `host_wii_pointer`; buttons → the native Wii input; haptics on fire.
- Harness on Android: test sockets in the abstract namespace; `adb forward tcp:N localabstract:uc-test-<name>-cmd`; `scripts/uctest` transport gains a TCP mode.
- Gate: `uctest run train_gameplay` passes on the Quest; a manual-aim smoke (controller ray moves the reticle) checked from a capture.

### Task B3: flat baseline measurement
- Per-pass GPU timings (timestamp queries per packet, already in `pass_timer`), `ovrgpuprofiler` counters, crcs GPU level, game FPS, in chapter 1. This is the number Phase D improves; it also tells whether CPU or GPU binds first.

## Phase C — stereo

### Task C1: multiview through the 3D part of the frame
- Packet classification: 3D (perspective scene, its EFB copies and the post chain up to the scene boundary's end) vs 2D (HUD after it). Targets of 3D packets are 2-layer; their EFB copies 2-layer arrays; every sampled texture binding becomes `Texture2DArray` (1-layer for normal textures, a per-slot layer select pushes `ViewIndex` or 0).
- Vertex shader: `projection = push.eye[ViewIndex]` for perspective draws (a push-constant pair replaces the single matrix; ortho draws keep one).
- Effects passes that run on 3D targets (bloom etc.) either multiview-aware or off in VR (decided by D measurements).
- Gate: both eyes captured from the XR swapchain show the scene with correct parallax; HUD on the quad layer; title/menus still on the quad.

### Task C2: per-eye camera and comfort
- `renderer/xr/stereo_camera.{h,cpp}` (pure math, unit-tested on the host): eye frusta from fov tangents + game near/far; eye offset in game units (scale tunable, default from the game's units: measure a known object, e.g. door height); yaw recentring.
- Aim in stereo: ray in game view space, projected with the mono projection; reticle at hit depth on the quad (or drawn in the scene) — decided by playtest captures.
- Gate: unit tests for the math; on device, head turns look around inside the on-rails view, aim hits where the controller points (hit test against a known target in a scripted run).

## Phase D — GPU optimisation (Quest-measured)

Each change: before/after on the same scripted chapter-1 run, per-pass GPU ms + ovrgpuprofiler, two runs each; keep only what wins. Candidates, roughly by expected gain on a tiler:
1. Load/store ops: CLEAR/DONT_CARE where the guest clears or overwrites the whole target; depth DONT_CARE on store after the last use; no LOAD of a previous pass's attachment the next pass fully covers.
2. Fewer full-screen transfers: render the final 3D image straight into the XR swapchain array image (no EFB→slot→swapchain blits).
3. Foveation (XR_FB_foveation; fragment density map on the swapchain and the full-size 3D targets).
4. Eye resolution and render scale; effects (bloom, scene path) off or cheaper on Quest.
5. Merging small post-chain passes; EFB-copy mip chains only when sampled with mips.
6. One submission per frame instead of per packet; descriptor updates batched.
7. Display/game rate choice (72/90/120 Hz × 30/60 game fps) and pipeline seeds for Adreno (no on-device compile hitch).

## Risks
- Multiview through EFB copies is the deepest change; if a post-chain effect samples copies in ways multiview can't express, fall back to recording the 3D packets twice (per-eye command buffers) for that effect.
- The game runs at 30 fps natively; head motion between game frames relies on compositor reprojection unless the last frame is re-rendered with a new head pose (a later step if judder is bad).
- Adreno lacks BC formats: BC7 replacement textures (mods only) disabled on Android.
- The headset is shared with another session; runs wait on `quest3-lock`.
